# ADR-0001: A native C99 simulation compiled to WebAssembly

- **Status:** Accepted for the PHASEONE-001 design; implementation not yet begun
- **Date:** 2026-11-14
- **Decision owner:** QSOL-IMC
- **Scope:** First technical demonstrator, not an immutable commitment for every future subsystem

## Context

A browser game can be authored directly in JavaScript and web APIs, but PhaseOne asks a different question: **can one game-oriented native simulation be compiled and exercised both outside and inside the browser, while web APIs remain the presentation layer?**

The goal is a small, inspectable proof of that boundary. Reproducing an existing proprietary game or engine is neither needed nor acceptable.

## Decision

- Write the authoritative **gameplay/simulation core in ISO C99** with no browser APIs.
- Compile the same source for a **Linux native headless runner** and for **WebAssembly** using Emscripten/LLVM.
- Use **WebGL 2** via a minimal JavaScript browser host for initial presentation. Supply input and rendering snapshots over a documented, versioned host/WASM boundary.
- Keep simulation at a **fixed 60 Hz tick** (subject to later measured adjustment), with deterministic seeded pseudo-randomness and explicit integer-state serialization.
- Prefer primitive, procedural, original assets for PHASEONE-001.
- Treat compiler/toolchain dependencies as build-time dependencies; ship only static browser assets and required generated WASM/JS glue.
- Pin exact build versions after obtaining a known-good executed build; do not claim that such a pin or comparison exists today.

## Why this option

It isolates the *game logic* from the browser and allows native testing, while producing browser-ready execution without requiring a heavyweight client runtime. C99 is widely supported, auditable, and aligns with the project's minimal-dependency preference.

## Alternatives considered

| Option | Why not for PHASEONE-001 |
| --- | --- |
| JavaScript-only / browser-first | Already understood; does not test the new compilation model |
| Full native game engine exported to web | Faster content authoring, but obscures the minimal engine/host boundary |
| Haxe or another source-to-JavaScript language | Valid alternative; tests a different target path |
| C++ and large existing native frameworks | Useful later, but unnecessary complexity for first proof |
| Direct WebGPU as mandatory baseline | Adds compatibility and adapter complexity before the basic path is proven |
| Attempted port of an existing commercial game | Provenance, rights, complexity, and research reproducibility are unacceptable |

## Consequences and limits

- **Good:** identical game core sources can be exercised in independent hosts; native testability and a static browser deployment are possible.
- **Costs:** two build targets, a carefully specified ABI, browser lifecycle handling, input normalization, and additional CI/replay evidence.
- **Not implied:** native/WASM bitwise equality for arbitrary floating-point operations, graphics-identical output, an offline-installed PWA, performance parity with a native renderer, or absence of third-party compiler tooling.
- **Revisit when:** measured WASM bottlenecks, browser constraints, or a larger game design justify changing the language or renderer. Preserve the experiment's original result and rationale.
